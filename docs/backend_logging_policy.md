# Backend Logging Policy

Backend logging must support two goals at the same time:

- Operators can understand important service lifecycle and degraded-state events from `info` or higher logs.
- Routine agent-turn details remain available at `debug` without flooding normal runtime logs.
- Developers should not have to read raw JSON during normal local development.

This policy exists for GitHub issue #75: backend logs currently look structured because messages contain `key=value` text, but those values are not real structured fields. The current formatter in `backend/src/logger.py` only emits `%(message)s`, so fields such as `conversation_id`, `turn_id`, `provider`, `model`, and `tool_count` cannot be searched or aggregated reliably by a log collector.

## Level Boundary

Use `debug` for high-volume or implementation-detail events:

- per-turn agent invocation start/completion;
- per-turn TTS completion, chunk counters, and skipped optional speech events;
- cache hits and cache expiry details;
- tool registry and RAG MCP details such as source skip/load, registered tool count, full tool name lists, duplicate rename details, disabled-by-configuration state, and MCP compatibility renames;
- LLM object creation when it can happen lazily or repeatedly through factories;
- ignored internal graph or node events that do not affect client-visible behavior.

Use `info` for low-volume lifecycle or externally meaningful state changes:

- service startup and version;
- one-time runtime configuration summary that contains no secrets;
- request or conversation boundary events that intentionally change behavior, such as ignoring a chat invocation because no valid `conversation_id` exists;
- operator-facing audit events that should remain visible at the normal production log level.

Use `warning` for recoverable but abnormal conditions:

- optional or required dependency configuration is missing while the feature is expected to run;
- a cleanup or fallback path could not complete, such as an expired thread that cannot be deleted by the checkpointer;
- upstream or tool configuration is inconsistent but the process can continue.

Use `error` or `exception` for failed operations:

- request handling failed and returned a 5xx response or SSE error event;
- graph, LLM, MCP, TTS, or persistence execution failed;
- unexpected exceptions crossed a module boundary.

Use `logger.exception(...)` inside exception handlers so traceback data is retained. Add structured context to the exception log whenever the context is known.

| Request and stream failures | `backend/src/django_backend/urls.py` | `exception` with available request context |

## Structured Field Contract

Do not encode operational fields only inside the log message. Pass values through `extra={...}` so code uses structured fields consistently.

The default backend stdout renderer must be human-readable structured text, not raw JSON. In interactive terminals it may use ANSI colors for scanability, but non-TTY output must remain plain text without color codes. Render structured fields after the message in a stable `key=value` shape, for example:

```text
2026-06-22T07:26:16.508Z INFO [app] backend service starting | event=service.starting service="SKN28 Backend" version=0.1.0
```

Every structured backend log should keep the human message stable and put queryable data in fields. Raw JSON logs may be added only as a deliberate separate sink or deployment-specific formatter, not as the default developer console output.

Required base fields:

- `timestamp`
- `level`
- `logger`
- `message`
- `event`

Common optional fields:

- `conversation_id`: frontend-issued conversation id; backend API currently receives this as `session_id`;
- `turn_id`: per-request trace id generated by the backend;
- `agent`: logical agent name, such as `main_agent` or `speech_text_agent`;
- `profile`: tool profile name;
- `source`: tool source or subsystem, such as `rag_mcp`, `local`, `llm`, or `tts`;
- `provider`: non-secret LLM provider slug;
- `model`: non-secret model id;
- `tool_count`: number of tools, not the full tool payload;
- `chunk_count`: number of emitted chunks, not payload content;
- `message_chars`: character count of a user message, not message content;
- `endpoint`: HTTP endpoint or transport boundary;
- `configured`: boolean feature/dependency availability;
- `reason`: stable machine-readable reason string;
- `duration_ms`: elapsed time when measured;
- `error_type`: exception class name for failures.

Recommended event names:

- `service.starting`
- `chat.invocation.ignored`
- `chat.invocation.started`
- `chat.invocation.completed`
- `chat.invocation.failed`
- `thread_context.ignored`
- `thread_context.expired`
- `thread_context.delete_failed`
- `agent.created`
- `tool_registry.profile_loaded`
- `tool_registry.source_loaded`
- `tool_registry.source_skipped`
- `tool_registry.source_tools_loaded`
- `tool_registry.cache_hit`
- `tool_registry.registered`
- `tool_registry.registered_tools`
- `tool_registry.tool_renamed`
- `rag_mcp.tools_loaded`
- `rag_mcp.tools_disabled`
- `rag_mcp.tool_names_loaded`
- `rag_mcp.tool_renamed`
- `llm.created`
- `llm.unavailable`
- `tts.completed`
- `tts.unconfigured`
- `tts.failed`
- `tts.event_ignored`

## Message Shape

Messages should describe the event, not duplicate every field.

Prefer:

```python
logger.debug(
    "chat graph invocation completed",
    extra={
        "event": "chat.invocation.completed",
        "conversation_id": conversation_id,
        "turn_id": turn_id,
    },
)
```

Avoid:

```python
logger.info(
    "chat graph invocation completed conversation_id=%s turn_id=%s",
    conversation_id,
    turn_id,
)
```

The second form can be useful for local plain-text logs, but it must not be the only place where fields exist.

## Sensitive Data Boundary

Never log secret values or secret-bearing payloads in message text or structured fields.

Do not log:

- API keys, access tokens, session tokens, passwords, private credentials, webhook signing secrets, or DSNs containing credentials;
- `Authorization`, `Cookie`, or `Set-Cookie` headers;
- full user prompts, full model responses, raw uploaded document text, or audio base64 payloads;
- full tool arguments or tool outputs unless they are explicitly reviewed and known to be non-sensitive;
- URLs that contain credentials, tokens, signed query strings, or private document identifiers.

Allowed with care:

- provider and model names;
- public base URLs after masking credentials and query strings;
- message length, token counts, chunk counts, tool counts, and duration metrics;
- boolean configuration state such as `configured=true`.

When a field may contain a credential-bearing URL, mask it before logging. Keep only scheme, host, and safe path when needed.

## Runtime Defaults

Use `RUNTIME_LOG_LEVEL=INFO` as the normal operator-facing level for shared environments such as staging and production. Local development schemas may use `DEBUG` while agent, tool, or TTS behavior is still being investigated.

Changing the default log level contract belongs in `backend/.env.schema`. Do not add new log-related environment variables unless the backend code reads them and the team needs them as a stable runtime contract.

Third-party client libraries and server runtime loggers should not emit routine `INFO` logs through the backend root logger. Keep `daphne.cli`, `daphne.server`, `httpx`, and `httpcore` at `WARNING` or higher unless actively debugging upstream/server behavior.

Daphne access logs are not emitted through the backend JSON formatter, so normal backend start commands should send access logs to a separate sink or disable them. Do not mix plain access log lines into the structured application log stream.

## Test Expectations

Logging changes should include at least a small smoke test when formatter behavior changes.

Minimum useful assertions:

- structured formatter output includes `event` and extra fields;
- exception logs preserve traceback data;
- sensitive values are masked or omitted;
- hot-path routine logs are emitted at `debug`, not `info`.
